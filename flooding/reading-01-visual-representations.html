Computer vision · Prerequisite reading 01

What makes two pictures look alike?

A shoe search turns out to be a good way to think about what a vision model keeps, what it loses, and what we can reuse.

35–45 minutes, with time to explore the figures and questions · No coding required

You find a pair of trainers you like, take a photo, and try to find them online later. The shop had a wooden floor. The catalogue has white backgrounds. Your photo is slightly crooked; the catalogue shoes all face neatly to the left. You still expect the search to work.

That expectation asks quite a lot of a computer. It has to treat some differences as irrelevant while keeping the ones you care about. A change of background should probably be fine. A different sole or a missing logo might mean it has found the wrong shoe.

In Teaching Computers to See, we saw a model take a shortcut by relying on background colour. The shoe search brings us back to that problem, but from inside the model: what information does it keep between the pixels and the prediction? That is where a representation comes in.

Set aside 35–45 minutes to read, look closely at the figures, and think through the questions along the way. The drawings, scores, and numerical examples are teaching illustrations rather than results from a trained model. Further reading is collected at the end.

The same shoe, or the same colour?

The trainers (or sneakers) below give us a small version of the search problem. One candidate has the right shape in a different colour. The other keeps the colour but changes the design. Before worrying about a model, it helps to notice that we could reasonably want either result.

You might barely notice a shoe moving a little to the right in a photograph. A pixel-by-pixel comparison notices immediately: many locations now contain different colours. Change the background and most of the image may change, even though the shoe itself stays the same.

Which would you click?

Looking at the three drawings, which result would you click for the same shoe design? Would you choose differently if you were matching a colour scheme?

Two reasonable searches

Candidate A preserves the shoe’s design, although the colours differ. Candidate B preserves the colours but changes the shape. Both choices can make sense. “Similar” needs a purpose: shopping for a particular model and choosing colours for a poster are different tasks.

A pixel-by-pixel comparison asks whether colours occur at the same locations. That can help find an almost identical copy of a photograph. It is less useful when the object moves, changes size, or appears against a different background. For shoe search, we need a description that keeps useful details of the shoe while tolerating some changes in how it was photographed.

In your earlier background experiment, a colour rule failed when the backgrounds changed. A shoe-search system faces a related choice: should background colour contribute to its description of the product?

What would you tell a friend?

Suppose you’re describing the shoe to a friend who can’t see the photo. You might mention its colour, the thick sole, the low ankle, and the laces. You would probably leave out the shop floor. Your description keeps some information and leaves other information behind. In computer vision, a description used this way is a representation. A useful measurement or pattern within it is often called a feature.

The pixel grid is a representation too, although a much longer one. Our short description is easier to compare, but “blue, low top, laces” could describe plenty of shoes. If two products differ only in a small logo, that description has already lost the detail we need.

A computer can work with the same idea if we write the description as numbers. For these invented shoes, let’s use [ankle height, sole thickness, redness], each on a scale from 0 to 1. Larger values mean a higher ankle, a thicker sole, or more red in the shoe’s colour. That ordered list is a feature vector. The order matters: we need to compare ankle height with ankle height, rather than accidentally comparing it with redness.

Now the program has something to compare. Shoes with similar values can appear near one another in its results. But we still have a choice to make about how much each measurement matters. Give colour a lot of influence and a red boot may end up closer to a red trainer than a blue version of the same trainer.

So far, we’ve chosen the measurements ourselves. A neural network can learn a representation instead. As training adjusts its weights, the network changes how it turns pixels into features. In the supervised learning from the earlier course, those adjustments favour features that help predict the labels. The resulting vector usually isn’t as easy to label as our little shoe description. Information about shape or colour may be spread across many entries.

The logo or the background?

For an exact shoe match, which details would you keep: the background, the side logo, the direction the shoe faces, or the sole shape? Now imagine you’re choosing something to wear with a red outfit. Does the same description still do the job?

What I would keep

For model identification, the logo and sole shape may help distinguish products. Background colour usually should not determine the answer. Left-facing and right-facing views may depict the same model, so we want some tolerance to that change. Colour becomes more useful when matching an outfit. The details that matter depend on the question, and even a useful feature can be hidden or unclear in a particular photo.

A closer look at a shoelace

A close-up of a shoe contains a lot of small clues: a lace crossing the fabric, a seam, the edge of the sole. Each affects nearby pixels. A convolutional neural network, or CNN, picks up local patterns by applying learned calculations to small regions. Later convolutional layers work on the representations that earlier layers produced.

Picture a small window moving across an image. At each position, a calculation combines the numbers inside the window. A particular set of weights might respond strongly where brightness changes from dark to light in one direction. Another set might respond to a different pattern. The output records how strongly that pattern appears at different locations.

The weights for that local calculation form a filter. We can use the same filter all over the image. A stripe doesn’t need an entirely different set of weights because it appears in the bottom-right corner instead of the top-left. This reuse is called weight sharing. Collect the responses into a grid and you have a feature map. A layer usually produces several maps, each recording a different response.

Figure 3 uses a hand-designed dark-to-light pattern so that you can follow the calculation’s purpose. In a trained CNN, filters are generally learned from examples. They do not come with instructions that say “find the shoelace.” Also, a strong response is not a complete object prediction. A light-dark boundary could belong to a shoe, a table, or the edge of a piece of paper.

Later layers combine information from earlier maps. After several layers, an output can depend on a larger region of the original image. A small patch may reveal a stripe; a larger region may distinguish that stripe as part of a sole. Networks also use operations that change map sizes and transform their values.

You may have seen neural networks drawn as “edges, then textures, then parts.” That picture helps explain how the available context grows. Real features can be harder to name, and a layer doesn’t have to perform one tidy, human-readable job. Two trained networks may arrive at quite different internal representations.

Weight sharing also does not make a model immune to every change. Rotating a shoe, hiding its logo, or shrinking it until the laces disappear can still alter the features. The generalization problems from your first lessons remain. A model’s design, or architecture, and its training data both affect which changes it handles well.

The same stripe in two places

A filter responds strongly to a white stripe on a trainer and to one painted on a road. That sounds unhelpful at first. Could the response still be useful once a later layer sees the surroundings?

What the surrounding pixels add

A local filter can supply a useful clue without identifying the whole object. The surrounding patterns may include laces, a curved sole, road texture, or lane markings. A later calculation can combine those clues over a larger region. Whether the trained network does this successfully still needs to be tested.

For the technical background to local connections, shared weights, and feature maps, see the Stanford CS231n notes on CNNs. You do not need the equations to continue.

Finding the neighbours

We can now return to the catalogue with a more useful way to compare pictures. Suppose a trained network gives us a feature vector for each image. We save the catalogue vectors, run your photo through the same network, and look for the closest saved vectors. The lists may contain hundreds of numbers, but the search follows the same idea as comparing our three-number shoe descriptions.

Finding close vectors is called nearest-neighbour search. There are several ways to measure closeness. For this reading, imagine comparing differences between the corresponding entries in two lists. We do not need to choose a particular distance formula to understand why the representation affects the results.

Figure 5 is a small, invented map with two named axes. It shows how closeness might work when there are only two measurements. A real learned vector usually has far more entries, or dimensions. To display such vectors on a screen, we often reduce them to two dimensions, and that reduction can distort distances. Seeing two dots close together on a display does not establish that their original vectors are close under the distance measure used for retrieval.

These vectors are also often called embeddings: they let us place images in a space where we can compare relationships. We still need to ask what kind of similarity the space captures. A model that separates shoes from cups may put two shoes close together while overlooking the tiny mark that gives them different product codes.

Image search and classification can use the same representation but produce different outputs. Search returns nearby catalogue images. A classifier takes the representation and predicts a category such as “trainer,” “boot,” or “sandal.” The final part that maps features to the task’s output is often called a head.

In your earlier course, the model returned scores for cat, cup, and rocket. Those scores are already tied to a particular label set. Features from before that final prediction can contain information useful for another task. A system that outputs only three category scores has discarded many distinctions that a richer internal representation might still contain.

A suspiciously red set of results

Your first five results are a red boot, a red sandal, and three red trainers. You wanted the same design in any colour. Before blaming the model, how could we compare the same shoe in two colours with two different shoes in the same colour?

A comparison worth trying

The result suggests that colour may have too much influence for your task. It does not establish the cause by itself. Compare the returned distances or rankings for the two controlled pairs. Also inspect the catalogue: if it contains only red footwear, the retrieval cannot reveal whether the representation handles other colours. Keep the query and candidate set fixed when comparing representations.

Starting with features someone has already trained

Now suppose your school wants to sort equipment photos into ball, racket, and shoe. You’ve collected a small set of labelled pictures. Starting a large network from random weights would mean learning useful visual patterns and the new categories from that collection. It would be helpful to start with some visual features already in place.

A pretrained model has already been trained before you adapt it to your project, often using a large collection of other images. Some of the resulting visual patterns may be useful for your photographs. Reusing what was learned for a new task is called transfer learning.

The feature extractor is the part of the network that converts an image into a representation. One approach keeps its weights fixed. Each new photo passes through it to produce a vector. We then train a new classification head using those vectors and our equipment labels. The head learns how the existing features relate to ball, racket, and shoe. This is called using a frozen feature extractor.

The word “frozen” can sound as though we’ve stopped the model from doing anything. We’ve only stopped those weights from changing. Images still pass through the extractor and can produce different vectors. Feedback from the new task updates the head, which learns to use those features to separate our equipment categories.

We could also allow some or all of the extractor’s weights to change. That’s fine-tuning, and it gives the representation a chance to adapt to our photos. There is a trade-off: a small dataset now influences many more weights. Fine-tuning may help with a distinction the original features missed, or it may overfit and disturb features that were already useful.

Consider two tasks. Sorting ordinary equipment photos may fit reasonably well with features learned from everyday objects. Detecting a tiny manufacturing crack on a shoe sole requires a much finer distinction. A model’s previous success at recognizing shoes does not show that its features preserve that crack. The second task needs evidence from its own examples.

There is one fairly ordinary way to spoil this setup: prepare the images differently from what the pretrained model expects. The image size, channel order, and range of pixel values all matter. A photo can look perfectly reasonable on your screen while the numbers reaching the model are in the wrong form. And resizing can remove a small detail before the model ever gets to use it.

You already know to keep fresh test examples. When choosing between frozen features and fine-tuning, use a separate validation set for those choices. Reserve a final test set to check the chosen system. If you repeatedly choose settings based on the test results, the test begins to influence your decisions, even if those pictures never directly update the weights.

Did the frozen model learn anything?

Someone uses a frozen extractor and trains a new head for ball, racket, and shoe. They’re pleased to have trained their first model. Is that a fair description, even though most of its weights never changed?

Where the learning happened

Learning happened in the new head. The extractor remained fixed. With fine-tuning, the head and the selected extractor weights could change. Both count as training; the difference is which parts are allowed to adapt. Neither method removes the need to evaluate on fresh images.

The distinction between frozen features and fine-tuning follows the Stanford CS231n transfer learning notes. Input preprocessing depends on the particular weights; the TorchVision model documentation provides examples.

The tiny logo that disappears

Imagine that the search now returns two almost identical shoes. The difference is a small symbol near the heel. If you wanted a similar style, that result might be fine. If you needed the exact product, it would be frustrating. I’d want to know where the symbol disappeared before changing the model.

The first place I’d look is the image the model receives. The symbol might be clear in the original photo and disappear when it is resized. Once that distinguishing detail is gone entirely, a different classifier can’t restore the missing visual evidence. A closer photo, or a crop of the original made before resizing, is worth comparing.

If the symbol survives in the input, we can look further along the process. The representation may give it little weight because broad shoe categories depend more on overall shape. Or the features may preserve a useful difference that the new head hasn’t learned to use, perhaps because there are too few examples or the product labels are inconsistent.

Test the explanation that fits the evidence you have. If resizing erased the mark, compare image preparation methods first. If the mark survived but the examples were labelled inconsistently, review those labels. Keep the other conditions fixed so you can interpret the result.

Before training it again

The tiny symbol is gone from the resized image. Would you first try a larger head, more training on those same images, or a crop that keeps the symbol visible? What would need to stay the same for that comparison to tell us anything?

Why I would try the crop first

Crop the original image before resizing it for the model. This addresses the observed loss of visual evidence. Use the same underlying train, validation, and test groups for both conditions; make the crop procedure consistent and keep the training choices fixed. Check that the cropped inputs preserve the mark. A crop may remove other useful context, so an improvement still needs to be measured.

Back to the catalogue

Back at the catalogue, the question is still whether the search finds the shoes you meant. A model can do well at recognizing footwear and disappoint you on an exact product match. That gives us something concrete to investigate: the photo, the features, or the decision made from them.

If you have a few minutes, these are the questions I would take back to a set of your own pictures.

A few questions to take with you
  1. A catalogue needs exact product matches. Why might a feature vector that separates shoes from cups still be inadequate?
  2. How does freezing a feature extractor differ from fine-tuning it?
  3. A two-dimensional plot shows two images close together. What should you avoid concluding from that picture alone?
  4. Your model confuses two objects. Give one possible problem with the input, and one with the representation.
Some notes on those questions
  1. Broad category features may overlook the small differences between products. The needed distinction must survive in the representation.
  2. Freezing keeps the extractor’s weights unchanged while a new head learns. Fine-tuning also updates some or all of the extractor’s weights.
  3. A projection can distort distances, and visual proximity does not establish that the representation suits the task.
  4. An input problem could be a blurred or missing mark. A representation problem could be failing to preserve that mark even when it is visible. These call for different experiments.

Our search has treated each image as a whole. A photograph with two pencils, a ruler, and a pair of scissors asks more of us: we may need to say how many objects there are and where each one is. That is the desk waiting in Reading 2.

A little further · A feature vector is not the same thing as the model’s weights

The weights are the parameters used to process an input. With a frozen model, those parameters stay the same as you pass in different images. The feature vector is an output of that processing, so it can change from image to image without a weight update. Training adjusts parameters; extracting features computes a representation using the current parameters.

CNNs are one family of visual models. Other families, including vision transformers, construct image representations differently. The questions in this reading still apply: which information survives, how is the representation used, and can it transfer to the new task?
